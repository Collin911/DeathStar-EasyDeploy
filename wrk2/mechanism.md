# wrk2 load generator
This document explains how the load generator works, its parameters, and how to interpret its behavior and results.  

---

## Basic Usage

```bash
wrk -t <threads> -c <connections> -R <rate> -d <duration> -s <lua_script> <URL>
```


## Parameters

### -t \<threads>
This parameter specifies how many worker thread are spawned by wrk2 to run the lua script. It is not directly related to the test, but rather an internal client-side parameter. It only affects how efficiently wrk2 can generate the load.

### -c \<connections>
The parameter specifies how many **persistent** TCP connections are maintained during the test. The connections may be **reused** to send multiple requests. It is not directly related to user sessions.

### -R \<req-per-sec>
The parameter defines the global rate of the traffic generation in terms of requests per second. This parameter controls directly the load on the server side.

### -d \<duration>
This is the total lasting time of a test session. Connections stay open for the entire duration. Requests are generated continuously during this window. 

### Relationship Between Parameters

The parameters define orthogonal aspects of the test:

- `-c` limits concurrency
- `-R` defines throughput
- `-d` defines total exposure time

The total number of requests made during the test is calculated as $R\times d$.


## Social Network App specific
Each request generated by the load generator represents a single user performing the specific action. 

User identities are selected uniformly at random from a configurable population size (`max_user_index`). No session or authentication state is maintained across requests.
### Compose Post Workload 
Each request simulates a user sending a new post. 

Post content is synthetically generated and includes:
- A fixed-length random text body (256)
- A random number of user mentions (0~5)
- Optional embedded URLs (0~5)
- Optional media attachments with randomly generated media IDs (0~4)

This design exercises backend parsing, storage, fan-out, and indexing logic.

### Home Timeline Read Workload

Each request simulates a user reading a portion of their home timeline.

- **Timeline window:** Each request reads 10 posts (`start` to `stop`) starting at a random offset.
- **Payload:** URL query parameters (`user_id`, `start`, `stop`).


This is a read-only workload which exercises database queries, caching, and timeline aggregation logic.

### User Timeline Read Workload
This one is similar to the previous one, the only difference is that it requests the user's own timeline.

### Mixed Workload
This script is a user-behavior simulator which calls the previous three kinds of workload according to probability. 
 - compose_post() → write operations (10%)
 - read_user_timeline() → single-user read (30%)
 - read_home_timeline() → multi-user aggregated read (60%)
